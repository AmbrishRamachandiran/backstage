Move a package's README into backstage.io/docs

You take one package, move its how-to content out of its GitHub README and into a page on the docs site, and leave a short README that links to the new page. This page shows exactly what moves, where it goes, and which files you touch.

1. Why 2. What moves 3. Section map 4. Where it goes 5. Files you touch 6. Mistakes 7. Using Copilot 8. Checklist

1Why we're doing this

backstage.io/docs is the official source of truth. Its search and its AI assistant, Kapa.ai, only read pages published on the docs site. They never see package READMEs on GitHub.

3Where each kind of README content goes

Use this table for any package, not just scaffolder modules.

README contentGoes toNotes
Title and one-paragraph "what is this"README DocsShort version in both places
Installation (yarn add, backend.add / app wiring)README DocsKeep it in both. People land on npm or GitHub first
Configuration (app-config.yaml keys)DocsCheck every key against config.d.ts
Usage, examples, templates, screenshotsDocsOne complete example beats five fragments
Reference tables (options, inputs, outputs, events)DocsCheck them against the schema in src/
Troubleshooting, TLS or certificate notes, caveatsDocsUse admonitions like :::note or :::danger
"Legacy backend system" or createRouter / PluginEnvironment setupDeleteThe legacy backend system has been removed. Reviewers ask for this to be dropped
Content that already exists elsewhere in /docsDeleteLink to the existing page instead of duplicating it
Link to the new pageREADMEUse the full https://backstage.io/docs/… URL. Relative links break on npm

NEW.changeset/<short-name>-docs.md

---

6Mistakes reviewers catch

Keeping a "Legacy backend system" section

It no longer exists. Drop it, along with any README text that mentions it. This was requested on #36784 and #36960.

Copying instead of moving

If the README still has the full config and examples, the job isn't done.

Trusting the old README

Defaults, required fields and option names are often wrong. Check them in src/ and config.d.ts.

Relative link in the README

It breaks on npm. Use https://backstage.io/docs/… in READMEs and relative .md links inside /docs.

Forgetting the sidebar or changeset

Without the sidebar entry the page is hard to find. Without the changeset, reviewers will ask you to add one.

Taking a package someone already claimed

Read every comment on #36703 and search open PRs first. Then comment to claim yours.

7Option B: let GitHub Copilot do the first draft

Copilot's agent mode in VS Code can read the package, draft all 5 files, and show you the diff. The repo ships .github/copilot-instructions.md, so Copilot already knows Backstage's rules for docs, changesets and style. You still own the result.

Steps

  1. Do the human steps first

    Pick a package, claim it on the issue, and create your branch from upstream/master.

  2. Open Copilot Chat in Agent mode

    In VS Code, open the Chat view and switch the mode dropdown to Agent. Pick a strong model.

  3. Paste the prompt

    Copy the prompt on the right and replace <PACKAGE> and <FOLDER>.

  4. Review every change

    Read the diff file by file. Open the source and confirm each config key, default and input. Ask Copilot "show me where in the source X is defined" whenever you doubt something.

  5. Format, commit, push and open the PR yourself

    Run yarn prettier --write <files>, then git commit -s. Don't let Copilot commit, push or write the PR description for you.

Package: <PACKAGE>   (for example @backstage/plugin-scaffolder-backend-module-sentry)
Folder:  plugins/<FOLDER>

Do the following, then stop and show me a summary. Do not commit or push.

1. Read plugins/<FOLDER>/README.md and the package source in plugins/<FOLDER>/src,
   including any config.d.ts and action/input/output schemas.
2. Pick the best /docs section for this package (docs/integrations/<provider>,
   docs/features/<feature>, docs/backend-system, or docs/conf) and tell me why.
   Use docs/integrations/azure/scaffolder.md as a structural example.
3. Create the new docs page with front matter (id, title, sidebar_label,
   description). Move the setup, configuration, usage and reference content
   into it. Follow docs/contribute/doc-style-guide.md.
4. Check every config key, default value, required flag and option name
   against the source code. Do not copy anything from the README you cannot
   confirm in the code. List every README statement that did not match the
   code, and what you wrote instead.
5. Do not include any "legacy backend system" setup (createRouter,
   PluginEnvironment, makeCreateEnv). Only the new backend system.
6. Add the page to microsite/sidebars.ts in the matching group.
7. Find links in /docs (excluding docs/releases) that point at this package's
   GitHub README and change them to relative links to the new page.
8. Trim the README to: title, a short overview, installation steps, and a
   "Documentation" section that links to the new page using the full
   https://backstage.io/docs/... URL.
9. Create .changeset/<FOLDER>-docs.md with a 'patch' bump for this
   package and a one-sentence, adopter-facing message.
10. Show me the list of changed files.
Backstage's AI policy, in short (CONTRIBUTING.md)
  • AI tools are welcome, but you must understand and be able to explain every line. "The AI did it" is not an answer.
  • Don't submit an AI-generated PR you haven't personally understood and checked. Maintainers close those without review.
  • If the PR is largely AI-generated, say so clearly in the description.
  • Write the PR description and review replies yourself. Keep them short and focused on why.
